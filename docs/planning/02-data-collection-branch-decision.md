# 데이터 수집 병합 기준안

## 문서 목적

이 문서는 제안서 기준으로 `data_collection` 브랜치와 `yh0519` 브랜치의 수집 관련 구현을 비교하고,
이번 단계에서 어떤 브랜치를 기준으로 삼는 것이 더 논리적인지 판단하기 위해 작성한다.

핵심 질문은 다음과 같다.

> 지금 프로젝트 목표가 우선 데이터 수집 단계까지라면,
> 어느 브랜치가 더 적절한 기준 브랜치인가?

---

## 1. 비교 대상

### `data_collection`

주요 특징:

- `main/collect_data.py` 중심의 독립 수집 구조
- `data/raw/`, `data/processed/`, `data/metadata/` 산출물 풍부
- 수집 범위가 넓고 메타데이터가 잘 남아 있음
- 수집 계획 문서와 수집 결과 문서가 있음

주요 문서:

- `data/01_data_collect_plan.md`
- `data/collection_report.md`

### `yh0519`

주요 특징:

- `src/collect.py` 중심의 파이프라인 통합형 구조
- 전처리, 모델링, SHAP까지 같이 묶여 있음
- 수집 코드도 있지만 분석 단계와 강하게 결합됨

주요 문서:

- `process.md`
- `day.md`
- `interpretation.md`

## 2. 제안서 기준과의 부합성 비교

### 2.1. `data_collection`의 장점

제안서 2.1 데이터셋 구성과 더 직접적으로 연결된다.

- FDR 기반 주가/거시지표 수집 범위가 넓다
- FRED 보조 지표, 반도체 업황 페이지, SEC 정보까지 시도했다
- 수집 성공/실패 이력이 남아 있다
- `source_catalog.csv`, `collection_summary.csv`, `failed_collections.csv` 등 근거 자료가 있다
- "무엇을 어디서 모았는가"를 설명하기 쉽다

즉 `data_collection`은 **수집 단계 프로젝트 산출물**로서 설명력이 높다.

### 2.2. `data_collection`의 약점

- 코드 구조가 `src/` 기반 메인 파이프라인과 자연스럽게 이어지지 않는다
- `main/collect_data.py`가 독립적으로 크고, 이후 분석 단계와의 접점이 약하다
- 원시 데이터와 생성 결과가 Git에 많이 섞여 있다
- 2011년부터 현재까지를 기준으로 해 제안서의 5~7년 범위보다 넓고, 스코프가 다소 퍼져 있다
- 핵심 피처, 확장 피처, 참고용 수집 자료가 구조적으로 분리돼 있지 않다

즉 **자료는 풍부하지만 구조는 다소 거칠다.**

### 2.3. `yh0519`의 장점

- `src/collect.py`가 향후 전처리/모델링과 이어지기 좋은 구조다
- 국내 종목 주가, 기본 거시지표, 수급 데이터 수집 함수가 있다
- 이후 단계와 연결하기 위한 코드 파이프라인 관점에서는 일관성이 있다

즉 `yh0519`는 **장기 구조 참고용**으로는 분명 가치가 있다.

### 2.4. `yh0519`의 약점

- 수집 단계보다 분석 단계에 무게가 많이 실려 있다
- 제안서의 핵심 분석 원칙을 지키지 못한 부분이 리뷰에서 확인되었다
- `SOX` vs `SOXX`처럼 컬럼명과 실제 소스 불일치 문제가 있다
- 수집 코드가 제안서 전체 수집 범위를 충분히 포괄하지 못한다
- 메타데이터/수집 결과 추적성은 `data_collection`보다 약하다

즉 `yh0519`는 **수집 기준 브랜치라기보다 분석 시도 브랜치**에 가깝다.

## 3. 핵심 판단

### 판단 1. 이번 단계 기준 브랜치는 `data_collection`이 더 적합하다

이유:

- 지금 목표가 우선 데이터 수집 단계까지이기 때문
- 제안서가 요구하는 "피처를 왜 수집했는지" 설명에 필요한 메타데이터가 더 풍부하기 때문
- 실패 내역과 소스 추적 정보까지 남아 있어 팀 공유 근거로 쓰기 쉽기 때문

즉 "지금 무엇을 모았는가"를 보여주기에는 `data_collection`이 더 논리적이다.

### 판단 2. 그렇다고 `data_collection`을 통째로 병합하는 것은 비추천이다

이유:

- 산출물과 코드가 과하게 뒤섞여 있음
- 향후 전처리/EDA 단계로 넘어갈 때 다시 구조를 손봐야 할 가능성이 큼
- 원시 데이터와 생성 결과의 Git 관리 기준이 불명확함

따라서 `data_collection`은 **기준 참고본**으로는 적합하지만,
그 브랜치를 그대로 메인 구현으로 병합하는 것은 별개 문제다.

### 판단 3. `yh0519`는 수집 단계 병합의 기준 브랜치로 보기 어렵다

이유:

- 제안서가 우선 요구한 것은 수집 체계 확립인데, 이 브랜치는 이미 분석으로 많이 앞서감
- 분석 신뢰성 이슈가 있어 브랜치 전체 신뢰도를 낮춘 상태임
- 수집 구현만 떼어봐도 범위와 추적성 측면에서 `data_collection`보다 우세하지 않음

즉 `yh0519`는 **수집 병합 기준**으로는 우선순위가 낮다.

## 4. 가장 현실적인 실행안

현재 가장 논리적인 선택지는 다음 셋 중 하나다.

### 선택지 A. `data_collection`을 기준으로 선별 병합

장점:

- 빠르다
- 기존 수집 결과를 최대한 활용할 수 있다

단점:

- 브랜치 구조가 정돈되지 않음
- 나중에 다시 정리할 일이 생길 수 있다

### 선택지 B. `main` 또는 현재 작업 브랜치에서 수집 코드 재구성

장점:

- 제안서 기준으로 필요한 피처만 깔끔하게 다시 설계 가능
- 산출물/코드/메타데이터 경계를 분명히 할 수 있음
- 이후 전처리 단계로 넘기기 좋음

단점:

- 시간이 더 든다
- 기존 코드 일부를 다시 옮겨 적어야 할 수 있다

### 선택지 C. `data_collection` 코드만 참고하고 새로 작성

장점:

- 가장 명확하다
- 필요 없는 산출물을 끌고 가지 않아도 된다

단점:

- 구현 부담이 있다
- 일정이 빠듯하면 부담될 수 있다

## 5. 추천안

현재 상황에서는 **선택지 B 또는 C가 가장 안전하다.**

즉:

- `data_collection`을 참고본으로 삼고
- `main` 또는 현재 작업 브랜치에서
- 제안서 기준 최소 수집 범위를 충족하는 수집 파이프라인을 다시 정리하는 방식

이 가장 논리적이다.

실무적으로는 아래처럼 정리하는 것이 좋다.

1. 수집 대상 피처를 제안서 기준으로 확정
2. `data_collection`에서 재사용할 코드와 데이터 소스를 선별
3. 실행 엔트리포인트 1개로 통합
4. 메타데이터와 실패 로그는 유지
5. 생성 산출물 커밋 여부는 별도 기준으로 결정

## 5.1. 왜 "처음부터 다 쓰지 않고 core부터"가 더 논리적인가

데이터를 많이 모으는 것과, 그 데이터를 1차 모델에 전부 넣는 것은 다른 문제다.

처음부터 모든 피처를 같은 중요도로 넣으면:

- 어떤 피처가 실제 성능에 기여했는지 알기 어렵고
- 정렬/결측치/시차 문제를 한 번에 떠안게 되며
- 설명 가능한 모델이라는 제안서 취지에도 오히려 불리해진다

따라서:

- 수집은 넓게 가능
- 공식 1차 파이프라인은 core 피처부터
- extended 피처는 이후 비교 실험으로

가는 것이 더 타당하다.

## 6. 최종 결론

이번 단계에서 "데이터 수집 병합"만 놓고 보면:

- **브랜치의 방향성과 설명 가능성은 `data_collection`이 더 낫다**
- **코드 구조의 일관성은 `yh0519`의 일부가 참고 가치가 있다**
- **하지만 둘 중 하나를 통째로 병합하는 것보다, `data_collection`을 참고해 새로 정리하는 편이 더 논리적이다**

가장 압축하면 아래처럼 정리할 수 있다.

> 이번 프로젝트 목표가 우선 데이터 수집 단계까지라면 `data_collection`이 더 적합한 기준 참고본이다.
> 다만 그대로 병합하기보다, 제안서 기준으로 필요한 수집 피처와 메타데이터 구조만 선별해 새 수집 브랜치에서 재구성하는 것이 가장 안전하다.
