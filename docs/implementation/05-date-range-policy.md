# 수집 기간과 모델 검증 구간 원칙

## 결론

현재 단계에서는 core와 extended를 모두 같은 기간 기준으로 다시 수집한다.
기본 수집 범위는 `2011-01-01`부터 수집 실행일 현재까지다.

다만 수집 범위를 넓히는 것과 모델 학습에 전 기간을 그대로 넣는 것은 다르다.
수집은 넓게 하고, 모델 검증은 기간을 나누어 진행한다.

---

## 왜 기존 core도 재수집해야 하는가

`data_collection` 브랜치 산출물은 대체로 2011년부터 2026년까지의 넓은 기간을 가진다.
반면 기존 현재 브랜치의 공식 수집 기본값은 `2018-01-01`부터 `2024-12-31`까지였다.

core와 extended를 서로 다른 기간으로 두면 전처리 단계에서 다음 문제가 생긴다.

- 날짜 index를 맞출 때 extended만 더 긴 구간을 가지고 core는 결측이 생긴다.
- 특정 기간의 시장 regime이 한쪽 피처군에만 반영된다.
- EDA에서 보이는 상관관계와 모델 학습에 들어가는 구간이 달라진다.
- B안처럼 extended 전체를 탐색하는 팀원이 core와 extended를 같은 기준으로 비교하기 어렵다.

따라서 재수집 시에는 core, collect-now extended, archive/reference 원천을 같은 실행 단위에서 수집한다.
수집 metadata에는 각 피처의 실제 `data_start`, `data_end`, `tier`를 기록한다.

## 권장 기간 분리

| 용도 | 기간 | 목적 |
|---|---|---|
| Raw 수집 | 2011년부터 현재까지 | 가능한 넓은 원천 데이터 확보 |
| EDA | 2011년부터 현재까지 | 장기 사이클, 결측, 구조 변화 확인 |
| A안 기본 모델 | 2018년부터 2024년까지 | core-only baseline 안정성 확인 |
| 최근 regime 검증 | 2025년부터 2026년 현재까지 | AI/HBM 반도체 붐 구간에서 일반화 확인 |
| B안 탐색 | 2011년부터 현재까지 또는 기간별 비교 | extended 전체 후보의 추가 설명력 탐색 |

2025년 이후는 AI/HBM 중심 반도체 장세가 강하게 나타난 구간이다.
이 구간은 발표 관점에서 중요하지만, 무작정 학습에 섞으면 최근 regime에 과적합될 수 있다.
따라서 A안에서는 2025년 이후를 최종 검증 또는 별도 최근 regime 테스트로 다룬다.

## data_collection 산출물과의 충돌 처리

현재 병합한 `data_collection` 산출물은 `data/raw/fdr/`와 `data/raw/external/`에 둔다.
현재 수집 파이프라인의 공식 실행 산출물은 `data/raw/runs/<run_id>/`에 저장된다.

따라서 파일 경로 차원의 충돌은 없다.
주의할 점은 전처리 단계에서 서로 다른 기간과 출처를 한 번에 섞는 것이다.

전처리에서는 다음 원칙을 따른다.

1. 모델링용 데이터셋은 하나의 기준 기간을 명시한다.
2. 모든 피처는 해당 기준 기간으로 windowing한 뒤 join한다.
3. 월간·분기·공시 기반 피처는 `period_end`가 아니라 `effective_from <= prediction_date` 기준으로 join한다.
4. `data/raw/fdr/` 산출물은 시간 단축용 재사용 원천이고, 공식 재현 run은 `data/raw/runs/<run_id>/`를 우선한다.

## 실행 판단

뉴스 감성을 제외한 extended 원천은 수집 또는 archive 보관까지 진행할 수 있다.
단, 이것은 모델에 전부 투입한다는 뜻이 아니다.

- A안: core-only baseline을 먼저 만들고, extended는 검증된 일부만 ablation한다.
- B안: extended 전체 raw pool에서 요인을 찾되, look-ahead와 중복 피처 문제를 별도로 검증한다.

두 방식 모두 같은 raw 수집 결과를 공유할 수 있다.
차이는 수집이 아니라 모델 투입과 검증 절차에 있다.
